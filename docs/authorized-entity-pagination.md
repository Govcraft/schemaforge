# Authorized entity pagination

GET `/api/v1/forge/schemas/{schema}/entities` and POST `/api/v1/forge/schemas/{schema}/entities/query` apply record authorization before response pagination and total counting.

`count` is the number of entities in the returned page. For authenticated callers requesting a total, `total_count` is the number of readable records matching the tenant scope and query filters, before the caller's offset and limit. Offsets skip readable records. Denied records neither contribute to the total nor leave gaps in a page. A filter that matches only denied records returns an empty page with a zero total. An offset beyond the readable end returns an empty page with the readable total unchanged.

Authorization still applies the configured operator record policy and Cedar checks to complete rows. Field projection, field access filtering, and relation enrichment occur after record authorization and page selection. This change does not alter owner semantics or any authorization rule. No count of withheld records is exposed. Anonymous responses continue to omit `total_count`.

PostgreSQL can count and page directly when the captured applicable Read policies exactly match generated rules and storage certifies that every decoded row conforms to the captured authorization schema. The proof includes generated tenant isolation, stored column types, required values and identifier representation. The page and count use one transaction snapshot. Custom applicable Cedar predicates, explicitly supplied record policies, unsupported storage shapes and other backends use the authorized scan described below. Totals remain exact in both paths.

JSON payloads are omitted from Cedar's resource schema and attributes, including required JSON fields. Their contents do not affect the certified Read decision, so PostgreSQL counts do not scan them for decoder limits. Selected rows still undergo normal decoding. An authorized row whose JSON cannot be decoded can contribute to the total when it is outside the page; selecting that row still returns the decoding error. Totals describe authorization, not a guarantee that every payload can be decoded. Failed checks on stored authorization values produce debug diagnostics naming the field and check category without recording row values.

Arbitrary record policies can require evaluating every matching candidate. The route reads candidates in batches of 256 and retains the requested readable page. For large collections, `count=false` on GET, or `"count": false` in a POST query, omits the total and stops scanning after filling the readable page. Deep offsets still require evaluating the preceding candidates. An omitted limit can still return all readable matches.

PostgreSQL and SurrealDB execute bounded, filtered, sorted candidate queries. The current SQL Server backend reads and filters the table internally for each query, so route batching does not bound its internal memory and repeated batches increase scan work. Fallback exact authorized counts can be substantially more expensive than a storage `COUNT(*)` and may exceed the configured request deadline on large collections. The optimization does not place a global time bound on arbitrary exact counts.

Queries use deterministic ordering with an ID tie-breaker. Fallback candidate batches do not share a database snapshot, so concurrent inserts, deletes, or changes to sort/filter fields can affect a scan or later pages. The response is an observation, not a retained snapshot. Backend failures abort the request instead of returning a partial page with a fabricated total.

Each query captures its Cedar policy snapshot and prepares principal/action state once. The actor-installed default Cedar adapter is not evaluated a second time; explicitly supplied operator policies still run alongside Cedar. `count=false` uses the page-only scan without the whole-table storage certification step.
